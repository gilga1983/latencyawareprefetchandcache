# Latency-aware cache and prefetch model v0.1

This document is the simulator contract. Policy experiments should not silently change these semantics; model changes should be versioned here first.

## 1. Workload

A demand request is

\[
r_i=(a_i,x_i,s_i),
\]

where `a_i` is simulated arrival time, `x_i` is an exact object identifier, and `s_i` is the object size in bytes. Requests are processed in nondecreasing simulated arrival time.

The simulated arrival time is intentionally separate from the raw timestamp stored in a trace. High-resolution traces may use their timestamp directly. Coarse traces can use a reconstruction layer. The default deterministic reconstruction for a coarse timestamp bucket `b` containing `m` requests places request `j` at

\[
a_{b,j}=bT+\frac{(j+1)T}{m+1},\qquad j=0,\ldots,m-1,
\]

where `T` is the number of simulator time units per coarse bucket. This preserves order and observed requests per bucket without treating every request in the bucket as simultaneous. A synthetic request clock `a_i=a_0+i\Delta` is also supported for controlled experiments.

## 2. Object state

At any simulated time an object is in exactly one data state:

- **ABSENT**: neither resident nor being fetched.
- **INFLIGHT**: one backend fetch exists with an issue time, completion time, size, and origin (`demand` or `prefetch`).
- **RESIDENT**: the completed object is held by the cache policy.

Only resident bytes consume cache capacity. In-flight bytes count toward backend traffic but not cache occupancy.

## 3. Backend model

Issuing a backend fetch for object `x` of size `s` at time `t` asks the backend model for latency

\[
L(x,s,t)\ge 0
\]

and schedules completion at `c=t+L(x,s,t)`.

Model v0.1 assumes independent backend operations: there is no queueing, concurrency limit, or prefetch-induced I/O contention. The implementation provides:

- constant latency `L`;
- integer affine latency `L_0 + ceil(s/B)`, where `B` is bytes transferred per simulator time unit.

Queueing and finite concurrency are future backend models, not changes to cache semantics.

## 4. Event order

For an external action at time `t`:

1. Process every backend completion with completion time `<= t`.
2. Process the demand at `t` (if any).
3. Update demand-visible predictor state.
4. Generate prefetch actions.
5. Schedule eligible prefetch fetches.

Thus, a fill completing exactly at demand time is resident for that demand. A prediction generated by a demand at time `t` has zero lead over another action at the same simulated time.

## 5. Demand semantics

For demand `(t,x,s)`, after completions through `t` have been processed:

### Resident hit

If `x` is resident, access latency is

\[
A_i=0.
\]

The cache policy receives a demand access and may update replacement metadata (e.g., LRU recency).

### Delayed hit on a prefetch

If `x` is in flight because of a prefetch with completion time `c>t`, no new backend request is issued and

\[
A_i=c-t.
\]

This is classified as a **prefetch-delayed hit**.

### Demand coalescing

If `x` is already in flight because of an earlier demand with completion time `c>t`, no new backend request is issued and

\[
A_i=c-t.
\]

This is classified separately as a **demand-coalesced hit** so ordinary request overlap is never credited to the prefetcher.

### New miss

If `x` is absent, the demand launches a backend fetch. If its backend latency is `L`, then

\[
A_i=L.
\]

Multiple later demands may join this fetch.

## 6. Prefetch semantics

A prefetch request names `(t,x,s)` after observing a demand.

- If `x` is resident, the prefetch is redundant and does not touch replacement metadata.
- If `x` is already in flight, the prefetch is redundant and does not launch a duplicate fetch.
- If `s>C`, where `C` is cache capacity, the v0.1 simulator suppresses the prefetch because the completed object cannot be retained.
- Otherwise a backend fetch is issued with origin `prefetch`.

A useful prefetch may therefore yield either a resident hit or a delayed hit. Prefetch usefulness is continuous in lead time, not binary.

## 7. Completion and cache semantics

Cache occupancy changes on **fetch completion**, not fetch issue.

When a backend fetch completes, the object leaves the in-flight table and the cache policy receives a fill event containing object, size, completion time, and fetch origin. The cache policy owns admission and eviction.

The baseline policy is a byte-capacity LRU:

- demand resident hits move the object to MRU;
- completed admitted fills enter at MRU;
- a prediction naming a resident object does not refresh it;
- evictions occur only as required by completed admitted fills;
- an object larger than the cache is fetched on demand but never retained.

Once resident, a demand-fetched object and a prefetched object obey the same replacement rules. Origin is retained only for accounting/policy hooks.

## 8. Primary objective

For `N` demands, the primary metric is average access time

\[
\mathrm{AAT}=\frac{1}{N}\sum_{i=1}^N A_i.
\]

Resident-hit ratio remains diagnostic. Delayed hits must not be collapsed into a hit/miss bit because two delayed hits can hide very different fractions of backend latency.

The simulator also records resident hits, prefetch-delayed hits, demand-coalesced hits, new misses, backend fetches/bytes, prefetch fetches/bytes, redundant prefetches, and oversize suppressions. Tail-latency statistics will be added when trace execution is wired in.

## 9. Residual latency value

For paired executions of the same demand stream, let

- `A_i^C` be access latency under a reactive cache with demand fetching only;
- `A_i^{C+P}` be access latency under the corresponding cache plus prefetcher.

Define per-request marginal latency gain

\[
G_i=A_i^C-A_i^{C+P}.
\]

This is the latency-aware generalization of residual prefetch value. `G_i=0` means no marginal benefit, `0<G_i<L` captures a useful late prefetch, `G_i=L` captures a full residual miss avoided, and `G_i<0` is possible when prefetch-induced cache pollution hurts a later demand.

Ignoring eviction and assuming fixed backend latency `L`, a prediction issued `d` time units before a residual demand has direct latency value

\[
V=\min(d,L).
\]

This produces the required sanity curve for `L=10`: lead times `0,2,5,10,20` save `0,2,5,10,10` time units.

## 10. Invariants

The v0.1 implementation tests the following invariants:

1. Simulation time never moves backward.
2. At most one backend fetch for an object is active at a time.
3. A resident prediction never changes cache recency.
4. A second demand for an in-flight demand fetch coalesces and creates no backend traffic.
5. A demand for an in-flight prefetch waits only for the remaining latency.
6. Completions at time `t` are visible to a demand at `t`.
7. Cache capacity is enforced at fill time.
8. Oversize prefetches are suppressed; oversize demand reads still execute but are not retained.
9. With fixed latency 10, lead times `0,2,5,10,20` save exactly `0,2,5,10,10`.

## 11. Explicitly outside v0.1

The first model intentionally excludes backend queueing, finite I/O concurrency, cancellation, partial-object streaming, partial fills, network/storage contention, write semantics, and multiple cache tiers. These can be introduced as replaceable models after the independent-I/O simulator is validated.
